## 1. 배경

### 1.1 문제 상황

Docker 컨테이너에서 6개 동시 요청부터 Engine Core 프로세스가 crash하는 문제가 발생했다.
GPU 메모리(A6000 48GB)는 여유가 있었으나, `max_num_seqs`, `max_num_batched_tokens`, `gpu_memory_utilization` 등
vLLM 설정을 아무리 변경해도 해결되지 않았다.

**원인은 vLLM 설정이 아닌 Docker 컨테이너 환경 설정 누락이었다:**

| 설정 | 기본값 | 수정값 | 역할 | 영향도 |
|------|:---:|:---:|------|:---:|
| `shm_size` | 64MB | **16GB** | `/dev/shm` 확장 — SharedMemoryConnector가 Stage 간 코덱 토큰을 전달하는 데 사용 | **결정적** |
| `OMP_NUM_THREADS` | 전체 코어 수 (32) | **8 / 16** | OpenMP 스레드 수 제한 — 과다 스레드 생성으로 인한 context switching 방지 | 보조적 |

### 1.2 왜 6개에서 crash했는가

vLLM-Omni의 2-Stage TTS 파이프라인은 SharedMemoryConnector로 Stage 간 데이터를 전달한다:

```
Stage-0 (Thinker) ──[/dev/shm]──> Stage-1 (Code2Wav)
```

Docker 기본 `/dev/shm` = **64MB**. 동시 요청이 증가하면 `/dev/shm` 사용량이 선형으로 증가하여
6개 요청에서 64MB를 초과 → SharedMemoryConnector 메모리 할당 실패 → Engine Core crash.

이 제한은 GPU 종류(3090/A6000)와 무관한 **호스트 OS 레벨** 제약이므로, 양쪽 서버에서 동일하게 6개에서 crash했다.

### 1.3 docker-compose.yml 변경 사항

```yaml
services:
  vllm-qwen3-tts:
    shm_size: '16gb'              # 핵심: /dev/shm 64MB → 16GB
    environment:
      - OMP_NUM_THREADS=8         # 보조: 과다 스레드 방지
```

`shm_size` 추가 후 20개 동시 요청까지 성공. 이후 `OMP_NUM_THREADS` 값(8 vs 16)에 따른 성능 차이를 비교 측정했다.

### 1.4 서버 환경

| 항목 | aiengine2 (LLM 서빙용) |
|------|:---:|
| GPU | NVIDIA RTX A6000 x 4개 (48GB x 4 = 192GB) |
| CUDA | 13.0 |
| CPU | AMD EPYC 7502 (32 Core / 32 Thread) |

## 3. 분석

### 3.1 성능 차이 없음

- **TTFA 차이**: -16% ~ +10% 범위에서 불규칙 변동, 일관된 방향 없음
- **총 소요 차이**: -7% ~ +11% 범위, 대부분 ±3% 이내
- **성공률**: 양쪽 모두 20/20 전체 성공

변동폭이 측정 오차(네트워크 지연, 스케줄러 타이밍) 범위 내이며, 두 설정 간 통계적으로 유의미한 차이는 없다.

### 3.2 왜 차이가 없는가

TTS 파이프라인의 병목은 **GPU 연산**이다:

```
Stage-0 Thinker (AR 토큰 생성) → GPU bound
Stage-1 Code2Wav (코덱 → PCM)  → GPU bound
```

CPU는 텐서 전처리, 토크나이징, SharedMemoryConnector 데이터 복사 등 가벼운 작업만 담당한다.
8스레드로도 CPU가 병목이 되지 않으므로, 16으로 올려도 GPU 대기 시간만 늘어날 뿐 실질적 이득이 없다.

### 3.3 구간별 특성 (공통)

| 구간 | 동시 요청 | TTFA | 총 소요 | 특징 |
|------|:---:|:---:|:---:|------|
| 안정 | 1~8개 | < 1.1초 | 선형 증가 | 모든 요청이 단일 배치로 처리, 실시간 여유 충분 |
| 전환 | 9~10개 | 1.2~2.5초 | 10~11초 | 스케줄러가 2배치로 분할 시작, TTFA 급등 |
| 포화 | 11~20개 | 2~7.6초 | 11~17초 수렴 | GPU 포화, 총 소요는 완만하게 증가하지만 TTFA가 급격히 상승 |

## 5. OMP_NUM_THREADS의 실제 역할

`OMP_NUM_THREADS`는 성능 향상이 아닌 **안정성 확보**를 위한 설정이다.

| | 미설정 (기본값=32) | 8 또는 16 |
|---|---|---|
| 스레드 수 | 전체 CPU 코어 수 (32) | 제한됨 |
| context switching | 과다 → 오버헤드 | 적정 |
| NUMA 접근 | 원격 메모리 접근 빈번 | 로컬 메모리 위주 |
| 메모리 사용 | 스레드당 스택 할당 → 과다 | 절제 |

기본값(전체 코어)을 사용하면 PyTorch/OpenMP가 불필요하게 많은 스레드를 생성하여 오히려 성능이 저하되고, `/dev/shm` 부족과 결합하면 프로세스 crash를 유발할 수 있다.

## 6. 결론

| 항목 | 결론 |
|------|------|
| 6개 crash 원인 | Docker 기본 `/dev/shm` 64MB 부족 — **`shm_size: '16gb'`로 해결** |
| 8 vs 16 성능 차이 | **없음** — 변동폭이 측정 오차 범위 내 |
| 권장 설정 | **`OMP_NUM_THREADS=8`** — 더 적은 리소스로 동일 성능 |
| 핵심 병목 | GPU 연산 (CPU 스레드 수와 무관) |
| A6000 VRAM 여유 | ~22 GB — GPU 메모리는 전혀 병목이 아님 |
| 최대 동시 요청 | **20개** (전체 성공, TTFA 7.6초 / 총소요 16.6초) |

### 권장 docker-compose.yml

```yaml
services:
  vllm-qwen3-tts:
    shm_size: '16gb'              # 필수: 6개 이상 동시 요청을 위한 공유 메모리
    environment:
      - OMP_NUM_THREADS=8         # 권장: 과다 스레드 방지 (8이면 충분)
```

### 운영 권장 기준 (A6000 단일 GPU, 0.6B 모델)

| 구분 | 동시 요청 수 | 근거 |
|------|:-----------:|------|
| 최적 (안정+효율) | **3~5개** | TTFA < 700ms, 총소요 선형 증가, RTF 여유 충분 |
| 허용 (서비스 가능) | **6~8개** | TTFA ~1초, 총소요 < 10초, 실시간 처리 가능 |
| 대기 허용 | **9~15개** | TTFA 2~5초, 큐잉 발생하나 전체 성공 |
| 한계 | **16~20개** | TTFA 5~7.6초, 대기 시간 길지만 crash 없음 |

## 7. 향후 확장 전략: 다중 GPU를 활용한 처리량 최적화

### 7.1 현재 구성의 비효율

A6000 단일 GPU 실측 데이터가 보여주는 **자원 낭비**:

| 지표 | 실측값 | 판단 |
|------|:---:|------|
| VRAM 사용률 | 25.8 GB / 48 GB = **54%** | 22 GB 유휴 |
| avg GPU util | 35~76% | 절반 가까이 idle |
| avg power | 222~244 W / 300 W TDP | 73~81% |
| 5개 동시 TTFA | 700 ms | 양호하지만 GPU 1장의 한계 |

0.6B 모델은 Stage-0(~8GB) + Stage-1(~8GB) = **~16GB면 충분**하다.
A6000의 48GB VRAM은 이 모델에게 과분하며, 남는 22GB는 아무 역할도 하지 못한다.

### 7.2 다중 인스턴스 분산 구성 (권장)

**핵심 아이디어**: A6000 1장에 1개 인스턴스 대신, **16GB급 GPU 여러 장에 독립 인스턴스**를 띄우고 Load Balancer로 요청을 분산한다.

```
                    ┌──────────────┐
                    │ Load Balancer│
                    │ (Nginx/HAProxy)
                    └──────┬───────┘
               ┌───────────┼───────────┐
               ▼           ▼           ▼
         ┌──────────┐┌──────────┐┌──────────┐
         │ GPU-A    ││ GPU-B    ││ GPU-C    │
         │ Instance1││ Instance2││ Instance3│
         │ :30001   ││ :30002   ││ :30003   │
         │ Stage0+1 ││ Stage0+1 ││ Stage0+1 │
         └──────────┘└──────────┘└──────────┘
```

각 GPU에 **독립된 vllm-omni 인스턴스**(Stage-0 + Stage-1)가 올라간다.
요청이 들어오면 LB가 가장 여유 있는 인스턴스로 라우팅한다.

#### 단일 GPU vs 다중 GPU 성능 비교 (이론치)

| 구성 | 동시 5개 TTFA | 동시 15개 TTFA | 총 throughput |
|------|:---:|:---:|:---:|
| A6000 x 1 (현재) | 700 ms | 5,200 ms | 1x |
| 16GB GPU x 3 (분산) | ~700 ms | **~700 ms** (각 5개씩) | **~3x** |

> 다중 GPU는 개별 요청의 latency를 줄이지 않는다. 줄어드는 것은 **대기 시간**(큐잉)이다.
> 15개 요청이 3개 인스턴스에 5개씩 분산되면, 각 인스턴스는 "동시 5개"의 안정 구간에서 동작한다.

#### VRAM 요구사항

| GPU | VRAM | 0.6B 인스턴스 가능 여부 | 비고 |
|-----|:---:|:---:|------|
| RTX 3060 12GB | 12 GB | 가능하나 제한적 | KV cache 여유 부족, 동시 3~4개가 한계 |
| RTX 4060 Ti 16GB | 16 GB | **가능** | RTX 3090과 유사한 VRAM, 동시 5개 안정 |
| RTX 4070 16GB | 16 GB | **가능** | 4060 Ti 대비 연산 성능 우세 |
| RTX 3090 24GB | 24 GB | **가능 (검증 완료)** | tts-dev-001에서 실측 확인 |

> **최소 VRAM 16GB** 필요. Stage-0(~8GB) + Stage-1(~8GB)이 동시에 올라가야 하므로 12GB는 여유 부족.

| TTFA (5개) | ~700 ms |
| VRAM 활용률 | 54% |
| 장애 시 | **전체 서비스 중단** |
| 확장성 | 수직 확장 한계 (GPU 1장의 한계) |

#### 방안 B: 다중 중급 GPU + Load Balancer (권장)

```yaml
# 16GB GPU x 3 + Nginx LB
services:
  vllm-tts-1:
    environment:
      - NVIDIA_VISIBLE_DEVICES=0
    ports: ["30001:30000"]

  vllm-tts-2:
    environment:
      - NVIDIA_VISIBLE_DEVICES=1
    ports: ["30002:30000"]

  vllm-tts-3:
    environment:
      - NVIDIA_VISIBLE_DEVICES=2
    ports: ["30003:30000"]

  nginx-lb:
    image: nginx:alpine
    ports: ["30000:30000"]
    volumes:
      - ./nginx-tts-lb.conf:/etc/nginx/conf.d/default.conf
```

```nginx
# nginx-tts-lb.conf
upstream tts_backend {
    least_conn;                    # 최소 연결 수 기반 분산
    server vllm-tts-1:30000;
    server vllm-tts-2:30000;
    server vllm-tts-3:30000;
}

server {
    listen 30000;
    location / {
        proxy_pass http://tts_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 300s;    # TTS 스트리밍 대기
    }
}
```

| 항목 | 값 |
|------|------|
| 동시 안정 처리 | **15~24개** (5~8개 x 3) |
| TTFA (15개) | **~700 ms** (각 인스턴스 5개씩) |
| VRAM 활용률 | 각 GPU ~100% |
| 장애 시 | 1대 장애 → 나머지 2대로 서비스 유지 |
| 확장성 | GPU 추가로 수평 확장 가능 |

#### 방안 C: Stage 분리 (현재 비권장)

Stage-0(Thinker)과 Stage-1(Code2Wav)을 별도 GPU에 분리하는 구성.

```yaml
# qwen3_tts.yaml에서 devices 분리
stage_args:
  - stage_id: 0
    runtime:
      devices: "0"    # GPU 0: Thinker
  - stage_id: 1
    runtime:
      devices: "1"    # GPU 1: Code2Wav
```

| 항목 | 판단 |
|------|------|
| 이론적 이점 | 각 Stage가 전용 GPU를 사용, idle 구간 제거 |
| 현실적 제약 | SharedMemoryConnector가 같은 호스트의 `/dev/shm`을 공유해야 함 |
| 추가 오버헤드 | GPU 간 코덱 토큰 전송 시 PCIe 경유 + 메모리 복사 지연 추가 |
| 결론 | **방안 B(독립 인스턴스 분산)가 더 단순하고 효과적** |

### 7.4 비용 효율 비교

| 구성 | 예상 비용 | 총 VRAM | 동시 안정 처리 | 비용/처리량 |
|------|:---:|:---:|:---:|:---:|
| A6000 x 1 (현재) | ~500만원 | 48 GB (22 GB 유휴) | 5~8개 | 기준 |
| RTX 4060 Ti 16GB x 3 | ~165만원 | 48 GB | 15~24개 | **~10x 효율** |
| RTX 3090 24GB x 2 | ~300만원 | 48 GB | 10~16개 | ~3x 효율 |

### 7.5 주의사항

| 항목 | 내용 |
|------|------|
| PCIe 레인 | 메인보드가 다중 GPU를 x16/x8로 지원하는지 확인. x4 이하는 성능 저하 가능 |
| 전력/발열 | GPU 3장 합산 전력이 PSU 용량 이내인지 확인 |
| `/dev/shm` | 각 컨테이너마다 `shm_size: '16gb'` 설정 필요 |
| Voice 등록 | 각 인스턴스에 개별적으로 voice 등록 필요 (또는 공유 볼륨 활용) |
| 모델 확장성 | 향후 1.7B, 7B 이상 모델로 업그레이드 시 16GB GPU는 VRAM 부족. 로드맵에 따라 판단 필요 |

### 7.6 요약

| 현재 모델 기준 (0.6B) | 권장 |
|------|------|
| 소규모 서비스 (동시 5개 이하) | A6000 1장으로 충분 (현재 구성 유지) |
| 중규모 서비스 (동시 10~20개) | **16GB GPU x 2~3장 + LB** (비용 대비 처리량 최적) |
| 대규모 서비스 (동시 30개+) | 16GB GPU x 4장+ 또는 24GB GPU x 3장+ |
| 향후 대형 모델 계획 있음 | A6000 유지 권장 (48GB VRAM 필요) |
